# แผนพัฒนาระบบก๊วนแบด

เป้าหมาย: เป็นระบบเล็กที่ใช้กันในก๊วน แต่ทำแบบมืออาชีพ คือ
**โค้ดมีคุณภาพ · ทำงานลื่น · โครงสร้างชัด แก้ง่าย · คนใช้ไม่ต้องคิด**

เอกสารนี้แบ่งเป็น 4 ส่วน
1. สถานะปัจจุบัน (จากการตรวจโค้ดจริง)
2. มาตรฐานที่ทุกงานต้องผ่าน
3. โครงสร้างโฟลเดอร์เป้าหมาย
4. แผนงานเป็นเฟส พร้อมเกณฑ์ว่า "เสร็จ" คืออะไร

---

## 1. สถานะปัจจุบัน (ตรวจเมื่อ 31 ต.ค. 2569)

ขนาด: 70 ไฟล์ ~4,500 บรรทัด · unit test 25 ข้อ (เฉพาะ `src/domain`)

### สิ่งที่ดีอยู่แล้ว ให้รักษาไว้
- logic สำคัญ (จัดคู่ คิดเงิน พร้อมเพย์ สถิติ) อยู่ใน `src/domain` แยกจากฐานข้อมูลและมีเทสต์
- ทุก server action ตรวจสิทธิ์ฝั่งเซิร์ฟเวอร์ และใช้ zod ตรวจข้อมูล
- การจัดคู่ล็อกต่อรอบด้วย advisory lock ถ้าหัวก๊วนสองคนกดพร้อมกันก็ไม่จัดคนซ้ำ
- เงินเก็บเป็นสตางค์ (integer) ไม่มีปัญหาทศนิยม
- มี design token ชุดเดียว รองรับโหมดมืด ทุกหน้าพอดีจอ 390px

## 2. มาตรฐาน (Definition of Done)

ทุก PR ต้องผ่านเกณฑ์ต่อไปนี้ ข้อที่เครื่องตรวจได้ CI จะบังคับเอง

**โค้ด**
- [ ] `npm run check` ผ่าน (typecheck + eslint + prettier + unit test)
- [ ] วางไฟล์ตามกฎในหัวข้อ 3 (ESLint ตรวจทิศทาง import)
- [ ] logic ใหม่ที่ไม่ต้องแตะฐานข้อมูลอยู่ใน `domain/` และมีเทสต์
- [ ] action ใหม่ใช้ `asAdmin`/`asUser` + `inSessionLock` + `refresh.*` (ดู ADR 0004)
- [ ] ไม่มี string path ตรงๆ ให้ใช้ `paths.*`

**ผู้ใช้**
- [ ] งานที่ทำบ่อยในสนาม (จบเกม ขอพัก จ่ายเงิน) ทำได้ใน **ไม่เกิน 2 แตะ**
- [ ] แต่ละหน้ามีปุ่มหลัก (primary) แค่ปุ่มเดียวต่อสถานะ
- [ ] ใช้ได้ที่ความกว้าง 360px ไม่มีเลื่อนซ้ายขวา และใช้ได้ทั้งโหมดสว่างและมืด
- [ ] ทุก action มีสถานะกำลังทำ และมีข้อความผลลัพธ์ที่บอกว่าเกิดอะไรขึ้น
- [ ] ข้อความ error บอกว่าผิดอะไรและต้องแก้ยังไง ไม่ใช่ "เกิดข้อผิดพลาด" เฉยๆ
- [ ] การกระทำที่ย้อนไม่ได้ (ลบ จบรอบ) ต้องยืนยันก่อน หรือมีปุ่มย้อนกลับ

**ความลื่น (performance budget)**

| ตัวชี้วัด | เป้าหมาย |
|---|---|
| JS ที่โหลดครั้งแรกต่อหน้า | ≤ 130 KB (ตอนนี้ 103–120 KB) |
| เวลาเซิร์ฟเวอร์ตอบหน้ารอบที่กำลังตี (p95) | ≤ 300 ms |
| ข้อมูลที่ส่งต่อครั้งตอนอัปเดตอัตโนมัติ ถ้าไม่มีอะไรเปลี่ยน | ≤ 1 KB |
| เวลาจากกด "จบเกม" จนเห็นเกมใหม่ | ≤ 1 วินาที |
| Lighthouse (มือถือ) หน้า pay | Performance ≥ 90, Accessibility ≥ 95 |

## 3. โครงสร้างโฟลเดอร์เป้าหมาย

> ทำเสร็จในเฟส 1 แล้ว โครงสร้างปัจจุบันและกฎอยู่ใน [ARCHITECTURE.md](ARCHITECTURE.md) (ต่างจากแผนเดิมเล็กน้อย: ใช้ `asAdmin`/`asUser` แทน `defineAction`, `ui/` import `domain/` ได้)

แบ่งตาม **ฟีเจอร์** แทนการแบ่งตามชนิดไฟล์ เวลาแก้เรื่องไหนให้เปิดโฟลเดอร์เดียว

```
src/
├─ app/                        # Route เท่านั้น: หน้าบาง ๆ ที่ประกอบ feature เข้าด้วยกัน
│  ├─ (member)/                #   หน้าหลังล็อกอิน (layout มีเมนู)
│  ├─ (public)/                #   login, pay/[id], claim/[token], welcome
│  └─ api/                     #   auth, live version endpoint
│
├─ features/                   # หนึ่งโฟลเดอร์ = หนึ่งเรื่องที่ผู้ใช้เข้าใจ
│  ├─ sessions/                #   รอบตี: สร้าง แก้ เริ่ม จบรอบ ลงชื่อ
│  │  ├─ components/
│  │  ├─ actions.ts            #   server actions ("use server")
│  │  ├─ queries.ts            #   อ่านข้อมูล (server only)
│  │  └─ state.ts              #   deriveState: รวมข้อมูลรอบให้หน้าจอใช้
│  ├─ play/                    #   คอร์ท คิว จบเกม เปลี่ยนตัว ผลการแข่ง
│  ├─ billing/                 #   บิล หน้าจ่ายเงิน แจ้งโอน ยืนยันรับเงิน
│  ├─ finance/                 #   รายรับรายจ่ายรายเดือน
│  ├─ members/                 #   ทะเบียน โปรไฟล์ ผูกบัญชี
│  ├─ stats/                   #   อันดับ คู่หู ความครบของข้อมูล
│  ├─ settings/
│  └─ activity/                #   (ใหม่) บันทึกว่าใครทำอะไร
│
├─ domain/                     # Logic ล้วน ไม่มี I/O ไม่ import Prisma client
│  ├─ matchmaking.ts  fees.ts  results.ts  promptpay.ts  levels.ts
│  ├─ labels.ts                #   (ใหม่) ข้อความไทยของทุกสถานะ จุดเดียว
│  └─ *.test.ts
│
├─ ui/                         # Design system: ไม่รู้จักฟีเจอร์ใดๆ
│  ├─ button.tsx card.tsx badge.tsx field.tsx dialog.tsx
│  ├─ data-table.tsx           #   (ใหม่) แทนโค้ดตารางที่ซ้ำ 6 ที่
│  └─ action-bar.tsx           #   (ใหม่) แถบ "ทำอะไรต่อ" ด้านล่างจอ
│
├─ server/                     # โครงพื้นฐานฝั่งเซิร์ฟเวอร์
│  ├─ db.ts  auth.ts  viewer.ts
│  ├─ define-action.ts         #   (ใหม่) auth + zod + lock + revalidate + activity log
│  └─ lock.ts
│
└─ lib/                        # ใช้ได้ทั้งสองฝั่ง: format.ts, paths.ts (ใหม่), cn.ts

tests/
├─ integration/                # server actions กับ Postgres จริง (สิทธิ์ ล็อก ออกบิล)
└─ e2e/                        # Playwright: เดินครบทั้งรอบแบบผู้ใช้จริง
docs/
├─ ROADMAP.md                  # ไฟล์นี้
├─ ARCHITECTURE.md             # ภาพรวม + กฎการวางไฟล์
└─ adr/                        # บันทึกการตัดสินใจสำคัญ (ทำไมเลือกแบบนี้)
```

### กฎทิศทาง import (ESLint ตรวจให้)

```
app ──▶ features ──▶ domain
  │         │  ╲──▶ ui
  │         ╰────▶ server, lib
  ╰──▶ ui, lib
domain ──▶ (ไม่มี)        ui ──▶ lib เท่านั้น        feature ──✗──▶ feature อื่น (ยกเว้นผ่าน index.ts)
```

- ไฟล์ใน `app/` ห้ามเรียก `prisma` ตรงๆ ให้เรียกผ่าน `features/*/queries.ts`
- `domain/` ห้าม import อะไรจาก `server/` หรือ `features/`
- feature หนึ่งใช้ของอีก feature ได้เฉพาะสิ่งที่ export ผ่าน `index.ts` ของ feature นั้น

## 4. แผนงาน

ประมาณเวลาคิดจากคนทำ 1 คน ทำนอกเวลา (~8 ชม./สัปดาห์)

### เฟส 0 — แก้บั๊กและวางเครื่องมือ (1 สัปดาห์) ← ทำก่อนใช้จริง
| งาน | แก้ปัญหา |
|---|---|
| `cancelMatch` ยกเลิกได้เฉพาะเกมที่ `PLAYING` และรอบยังไม่จบ + ล็อกรอบ | P1 |
| `updateMatchResult` ล็อกรอบ | P2 |
| ลิงก์ผูกบัญชีหมดอายุใน 7 วัน (`claimExpiresAt`) | P12 |
| แก้การแสดงเวลาให้ใช้ formatter ที่ถูกต้อง | P13 |
| ESLint (next + boundaries) + Prettier + `npm run check` | P7 |
| GitHub Actions: check → prisma validate → build ทุก PR | P7 |
| ย้าย Playwright E2E (ครบรอบ: หัวก๊วน + สมาชิก) เข้า `tests/e2e` และรันใน CI | P8 |

**เสร็จเมื่อ:** CI เขียว · E2E ครบรอบผ่านใน CI · มีเทสต์ยืนยันว่ายกเลิกเกมที่จบแล้วไม่ได้

### เฟส 1 — จัดโครงสร้างใหม่ (1–2 สัปดาห์) ไม่เพิ่มฟีเจอร์
| งาน | แก้ปัญหา |
|---|---|
| ย้ายไฟล์เข้า `features/` `ui/` `server/` ตามหัวข้อ 3 ทีละ feature (ไม่เปลี่ยนพฤติกรรม) | P3, P4 |
| ย้าย query ที่อยู่ในหน้าไปไว้ใน `queries.ts` ให้หน้าเหลือแค่ประกอบ UI | P3 |

| `paths.ts`: ฟังก์ชันสร้าง URL ใช้ทั้งใน `<Link>` และ revalidate | P6 |
| `ui/data-table.tsx` + `domain/labels.ts` | P5 |
| `docs/ARCHITECTURE.md` + ADR แรก (ดูหัวข้อ "ตัดสินใจก่อนเริ่ม") | — |

**เสร็จเมื่อ:** ใน `app/` ไม่มี `prisma.` เลย · ESLint boundaries ไม่มี error · E2E ยังผ่านเหมือนเดิม · ไม่มีไฟล์เกิน 200 บรรทัด

### เฟส 2 — ความถูกต้องและความปลอดภัยของข้อมูล (1–2 สัปดาห์)

| PWA: ติดตั้งเป็นไอคอนบนหน้าจอ เปิดเร็ว | เปิดใช้ในสนามได้ทันที |
| โหมดจอใหญ่ `/sessions/:id/board` แสดงคอร์ทและคิวบนแท็บเล็ตหรือทีวีที่สนาม | ไม่ต้องถามหัวก๊วนว่าถึงคิวหรือยัง |

**เสร็จเมื่อ:** ผู้ใช้ใหม่ลงชื่อ → ขอพัก → จ่ายเงินได้เองโดยไม่ต้องอธิบาย (ทดสอบกับคนจริง 3 คน) · Lighthouse Accessibility ≥ 95

### เฟส 5 — ฟีเจอร์เพิ่ม (เลือกตามที่ก๊วนต้องการจริง)
เรียงตามที่น่าจะคุ้มที่สุด ทำทีละตัว แต่ละตัวต้องผ่านมาตรฐานหัวข้อ 2

1. **แจ้งเตือนผ่าน LINE** (Messaging API): รอบเปิดแล้ว / อีก 1 เกมถึงคิวคุณ / บิลออกแล้ว / มียอดค้าง
2. **ผู้เล่นใส่ผลเอง** โดยฝ่ายตรงข้ามกดยืนยัน (ถ้าโต้แย้งให้หัวก๊วนตัดสิน)
3. **ค่าใช้จ่ายพิเศษ**: ส่วนลด, ค่าน้ำ, จ่ายบางส่วน, ยกยอดไปรอบหน้า
4. **รูปแบบเกม**: 2 ใน 3 เซ็ต, ตีแบบจำกัดเวลา
5. **สมาชิกรายเดือน**: เหมาจ่ายรายเดือนแทนการจ่ายรายรอบ
6. **หลายก๊วนในระบบเดียว** (ดูหัวข้อถัดไป)

| เรื่อง | ทำไมต้องตัดสินใจตอนนี้ | ข้อแนะนำ |
|---|---|---|
